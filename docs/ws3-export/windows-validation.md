# WS3 Export — Hardware Validation List

> **Purpose.** The single list of every WS3 export item that cannot be closed without real
> Windows hardware, a real macOS-native (`npm run tauri:dev` / built app) session, or either. It
> is the entire answer to "what's left" for WS3 export hardening — if this list is complete, the
> architecture ledger is clean. **Nothing else lives here**: no architecture, no history, no
> rationale beyond one sentence per item. `docs/ws3-export/architecture-ledger.md`'s Round 16
> disposition table references these rows by ID and says nothing more about them. When an item is
> closed, record the run in the ledger's next round entry and delete the row here.
>
> Column contract, every row: **ID** · **What is unverified** (one sentence) · **The exact test**
> · **Pass criterion** (a number or an observable) · **What breaks if it fails**. Cross-references
> in parentheses are to the C/H finding IDs in `docs/ws3-export/pipeline-audit.md` Part 7 and the
> ledger's disposition table.

---

| W1 (H10) | Whether `ffmpeg_sweep_orphan_sessions`' `pending_delete` classification is accurate under a live NTFS delete-pending race, and whether `bytesReclaimed` excludes it. | On the built app, start an export, kill it, hold a file handle open on the orphaned session dir (e.g. `type` a piece file in a paused `cmd`), then start a new export so the sweep runs; read the sweep result on the startup notice. | The held dir appears in `pendingDelete`, not `removed`; `bytesReclaimed` excludes its bytes; a second sweep after releasing the handle removes it. | The startup notice over-reports reclaimed disk; the dir survives as an uncounted 1.6–2.3 GB leak. |
| W2 (H9) | Whether the real Win32 `CreateFile` family honours the `\\?\` prefix for every code path `copy_session_file_atomic` takes internally (open, streamed read/write, `rename_over`'s fallback). WS3 Round 18 CORRECTION: this row previously said "confirm the pre-encode check passes (it allows ≤ 32,767)" and named `std::fs::copy` as the code path under test — both wrong as of this repo. (1) `checkExportDestinationPathLength` (`exportDestinationPath.ts`) enforces `WINDOWS_MAX_PATH = 260` deliberately, not 32,767 — it is documented at its own definition (`windows_long_path`'s doc comment, `ffmpeg.rs`) as intentional fast-feedback/defensive-net belt-and-suspenders, not an attempt to express the real Win32 extended-length ceiling; Round 18 STEP 3 additionally tightened its effective limit to 255 to account for the `.part` suffix `save_session_file` now appends during delivery. A path in the 260(255)–32,767 range is REJECTED pre-encode by design, not passed through to test the `\\?\` prefix at delivery time — so this row's original test can never run as written. (2) `save_session_file` no longer calls `std::fs::copy` at all (Round 18 F2) — delivery is `copy_session_file_atomic`'s own open/stream-read/stream-write/`sync_all`/`rename_over`, all still `windows_long_path`-prefixed on both `src` and `dest`. | To actually exercise the `\\?\` prefix on the real delivery code path, bypass the TS pre-check (dev IPC console call to `save_session_file` directly, as W3 already does) with a `dest_path` whose full path is > 260 but < 32,767 chars (nest folders until `strlen` is e.g. 300); confirm `copy_session_file_atomic` succeeds and the `.part`→rename sequence completes. Separately (not the same test): confirm the OPERATOR-FACING pre-encode check still rejects that same path with `destination_path`/`checkExportDestinationPathLength`'s message before any rendering starts — that rejection is the current, intended UX for a normal export, not a bug. | The direct-IPC copy lands byte-identical (SHA-256) at the long path; the normal export flow rejects the same path pre-encode with a clear message, not a late delivery failure. | If the direct-IPC copy fails: the `\\?\` prefix doesn't actually cover every internal step of `copy_session_file_atomic`, and ANY future code path that reaches `save_session_file` without going through the operator-facing pre-check (a resume, a programmatic caller) can still fail at delivery after a full encode. If the pre-encode check does NOT reject a long path: it silently regressed from 260/255 back toward the real ceiling, reopening exactly the operator-confusion scenario STEP 10 (H9) introduced the check to prevent. |
| W3 (H9) | Whether a forward-slash separated or `..`/`.`-containing absolute Windows path resolves correctly once prefixed with `\\?\` (Win32 disables normalisation under that prefix). | Call `save_session_file` directly (dev IPC console) with `C:/Users/<u>/Videos/out.mp4` and with `C:\Users\<u>\..\<u>\Videos\out.mp4` as `dest_path`. | Both copies land at the intended canonical location, or both are rejected with a typed error before the copy — never a silent write to a literal `..` component or a failure only at copy time. | A dialog that ever emits such a path (third-party file pickers, drag-drop) fails delivery after a full encode. |
| W4 (H2) | Whether WebView2's `VideoEncoder` accepts `hardwareAcceleration: 'prefer-software'` with `avc1.640028` (High) at all, and what SPS/PPS/entropy mode the hardware (Media Foundation) and software rungs each emit, so a mid-file rung change is known to decode and mux. | Open `spike-parameter-sets.html` (Round 10) inside the Windows build; also run `VideoEncoder.isConfigSupported` for each ladder entry × each codec in `hardwareCodecLadder.ts`. | Every `(rung, codec)` pair's `supported` value logged; a hardware-then-software join of ≥ 60 pictures counts 60/60 in the native AU counter, decodes 60 in `VideoDecoder`, and muxes + decodes 60 in the sidecar with zero warnings. | Rung 5a failover cannot open an encoder (export fails where it should degrade), or the failed-over file is undecodable past the seam. |
| W5 (H3) | Whether Media Foundation / NVENC / QSV / AMF release a hardware encoder session synchronously on `VideoEncoder.close()`, so 23–27 sequential sessions plus abandoned flushes never exhaust the driver's session pool. | A ≥ 33-minute 1080p30 GL export (≥ 27 sessions) on the target GPU; read `encoderSessionsOpened`/`encoderSessionsClosed` from the diagnostics blob and the driver's session count (`nvidia-smi` / vendor tool) at rotation 20+. | Opened == Closed at every terminal post; driver-side session count never exceeds 1 (+1 during rotation); no `configure` failure after session 8. | Late-export encoder-configure failure surfacing as a rewind/failover that cannot succeed. |
| W6 | Whether `ffmpeg_kill_session` settles under `KILL_BOUND_MS = 125` ms on Windows (measured worst 5 ms on macOS; Windows uses `TerminateProcess` on a sidecar that may be mid-write). | Trigger a liveness-bound expiry mid-truncate (dev flag or a deliberately stalled 2.3 GB truncate) 10×; log `kill()` settle time. | Worst of 10 < 125 ms; no `FfmpegKillHungError`. | The bound's own expiry handler exceeds its bound; the operator is told the sidecar may still be running when it is not — or it is, and holds the session files. |
| W7 (H4) | Whether Windows Defender's synchronous scan-on-close accounts for the measured 12.4 ms/append (vs 0.5 ms on macOS). | Same 1080p30 export twice: once with `%TEMP%` (session dir) under a Defender folder exclusion, once without; read `appendIpcCallCount` and total wall time from the diagnostics blob; ProcMon on `ffmpeg_append_file_raw` if available. | Per-append cost with the exclusion ≤ 1/3 of without, or a ProcMon stack showing the AV filter on `CloseFile`. Either outcome closes the item; the number is what is missing. | Nothing breaks; the 512 KiB cap's wall-clock cost (6.96% at 12.4 ms) stays unexplained and cannot be attacked at its cause. |
| W7a (H4, WS3 Round 18 F1) | Whether Defender's scan cost is tied to `close()` (unaffected by chunking) or to `write()` count (multiplied by chunking). `ffmpeg_append_file_raw` now internally splits every batch into `IO_CHUNK_SIZE` (64 KiB) `write_all` calls inside the SAME open/close pair — still one open, one close, one `sync_all` per 512 KiB batch, but 8 `write()` syscalls instead of 1. If W7's eventual ProcMon trace shows the AV filter hooking `WriteFile` rather than only `CloseFile`, the 12.4 ms/append figure and the 6.96% cap-cost percentage this file and the architecture ledger both cite are wrong by roughly **8×** (12.4 ms → ~99 ms/append, 6.96% → ~56%) — not a rounding difference. | Run W7's own ProcMon capture and read which Win32 call(s) the AV minifilter attaches to, not just whether the exclusion A/B shows a cost difference. | The ProcMon stack names `WriteFile` (chunking is implicated, re-run the 512 KiB cost table with a real 8-call histogram) or only `CloseFile`/`CreateFile` (chunking is inert, W7's existing 12.4 ms figure stands unchanged). | Every downstream cost figure derived from 12.4 ms/append (this table's own wall-clock percentages, the architecture ledger's Round 16/18 cost tables) is silently wrong by up to 8× until this is checked — nothing crashes, but every "6.96%" citation is unverified pending it. |
| W8 (H6) | Whether a GPU Timeout-Detection-and-Recovery event during a long GL export presents as `gl-context-lost` and what survives it (Rung 5c is DEFERRED; the reopen trigger needs an observed instance). | During a ≥ 10-minute GL export, force a TDR (e.g. a GPU-hang test tool or a long shader stall) once. | The export fails with `failureVia: 'gl-context-lost'`, the session dir is resumable, a resume completes and the output matches an uninterrupted run's picture count. | Silent hang instead of a typed failure, or an unresumable session — either is a Rung 5c reopen observation. |
| W9 (H7) | Whether lid-close / Modern Standby kills the Media Foundation drain despite the worker heartbeat. | Close the lid (or `powercfg /sleep`) at session ~10 of a 27-session export; reopen after 2 minutes. | The export either continues to a correct picture count, or fails with a typed liveness error and a resumable session — never a silent stall past `FORWARD_PROGRESS_BOUND_MS` (45 s). | An export that is neither running nor failed; the operator waits indefinitely. |
| W10 (H5) | Whether two real app instances racing `reenter` on the same session UUID are serialised by the NTFS claim file, including the stale-PID recovery path. | Launch two built-app instances; crash an export in the first; have both take the resume offer within 1 s; separately, kill the holder and retry from the second. | Exactly one instance proceeds (`live_claim_blocked` on the other); after the holder dies, the second recovers with `staleClaimRecovered` and the session is not double-appended (picture count exact). | Two processes append to one `piece_N.h264`; the concat guard fails on a file no fence can repair. |
| W11 (H1) | Whether WebView2's raw-body IPC lands every byte of a single `appendFileRaw` above 512 KiB — the only measurement that would license raising `APPEND_BATCH_BYTES`. | Through the real Tauri/WebView2 raw-body path, append a known byte pattern at 512 KiB, 1 MiB, 1.5 MiB, 2 MiB, 3 MiB, 4 MiB; after each, compare `sessionFileSize` and a SHA-256 of the session file against the submitted bytes. | The largest size that lands byte-identical. | W12 (NOT DETERMINED #1/#2) | Real batched+back-pressure append throughput and terminal drain time on the 12.4 ms-class Windows machine (the Round 7 figures are SIMULATED). | The Round 7 harness scenario (`scripts/ws3-measure-append-throughput.test.ts`'s field chunk profile) reproduced as a real 1080p30 export; read `appendIpcCallCount`, `msSinceDone`, and the terminal drain from the diagnostics blob. | Terminal drain < 1,000 ms; peak `queueDepthBytes` < 32 MiB (the gate never engages). | `APPEND_DRAIN_BOUND_MS` (600 s) or `WATCHDOG_MS` (30 s) false-aborts a healthy export at the end. |
| W13 | The real per-call `open` / `write_all` / `close` cost of `ffmpeg_append_file_raw` on Windows, which every batching decision above has been reasoning about second-hand. | Instrument the three calls in `ffmpeg.rs`'s append command with timestamps (dev build), run one 1080p30 export, histogram the three. | p50/p99 for each of the three, in ms; whichever dominates names the mitigation (W7 if `close`, W11 if `write_all`). | Nothing breaks; the batch cap and the back-pressure threshold stay tuned against a guess. |
| W14 | The actual slice structure the Windows hardware encoder emits (multi-slice per picture inflates VCL-NAL counts 8× on some drivers — the reason Rung 1 exists). | Export 10 s on the target GPU; run `ffmpeg.countAnnexbFrames` on the session's `piece_0.h264` and compare `pictures` vs `vclNals`. | `pictures` == 300; `vclNals / pictures` recorded as the driver's slices-per-picture. | If `pictures` ≠ 300 the native AU scanner mis-parses that encoder's AU shape and every guard, salvage and checkpoint on Windows is wrong. |
| W15 | The cause of the two production Windows export hangs that started WS3 (never reproduced on macOS). | On a reproducing machine, run the same export with the Round 4+ diagnostics: `encoderSessionIndex`, `failureVia`, `encoderSessionsOpened/Closed`, `appendLedger`, plus the Windows Event Log for the process. | A typed `failureVia` and a session index at the hang, attributable to one of H1–H4. | Nothing new breaks; the mitigations shipped against H1–H4 remain hypotheses. |
| W16 (H5, WS3 Round 19) | Whether `GetProcessTimes` returns a creation time usable for PID-reuse detection — i.e. stable across reads of the same process, equal between the `GetCurrentProcess()` pseudo-handle (what the claim WRITES) and an `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, pid)` handle on the same PID (what liveness READS), and different for a new process that reuses a dead holder's PID. ## B. Needs a real macOS-native session (`npm run tauri:dev` or the built app)

| ID | What is unverified | The exact test | Pass criterion | What breaks if it fails |
|---|---|---|---|---|
| M1 | Whether WKWebView's VideoToolbox (`prefer-hardware`) and its software rung emit parameter sets that join cleanly — the Round 10 spike ran in Chromium, a different host, not where the app encodes. | Open `spike-parameter-sets.html` inside `npm run tauri:dev`; diff SPS/PPS per rung; join 30+30 pictures. | 60/60 in the native AU counter, 60 in `VideoDecoder`, 60 muxed + decoded by the sidecar with zero warnings. | A Rung 5a failover on macOS produces a file that stops decoding at the seam. |
| M2 (H3) | Whether VideoToolbox releases its hardware encoder session synchronously on `VideoEncoder.close()` across 27+ sessions. | A ≥ 33-minute 1080p30 GL export in the app; read `encoderSessionsOpened`/`encoderSessionsClosed` at the terminal post. | Opened == Closed; no `configure` failure at any rotation. | Late-export encoder-configure failure on macOS. |
| M3 (H5, WS3 Round 20 carry-over) | Whether the macOS claim-liveness gap is fail-safe in practice. The `#[cfg(unix)]` arms of `process_start_time_ms` / `is_holder_process_live` (`session_claim.rs`) read `/proc/<pid>/stat` and `/proc/stat`; macOS has no procfs, so every `fs::read_to_string` fails, the writer records `start_time_ms = now_ms()` and the reader hits "PID exists but start time unreadable — treat as live". Liveness on macOS therefore collapses to `kill(pid, 0) == 0` — "a process with this PID exists" — with no PID-reuse detection, while the function's doc comment claims start-time matching. Direction of failure: a reused PID reads as LIVE, so the worst case is refusing to recover an abandoned session (`live_claim_blocked` until that unrelated process exits), never stealing a live one. | In `npm run tauri:dev`: start an export, `kill -9` the app, note the holder PID in `claim.json`; spawn a long-lived unrelated process and force it onto that PID (or wait for natural reuse — on macOS PIDs recycle within ~10⁴ spawns; `for i in $(seq 1 20000); do true & done` accelerates it); relaunch the app and take the resume offer. Separately confirm the same steps with the holder PID genuinely free recover with `staleClaimRecovered`. | With the PID reused: `live_claim_blocked` (safe refusal), never a recovery that appends to a dir another live process could own. With the PID free: `staleClaimRecovered`. Fix direction if the refusal matters in the field: replace the `/proc` read with `sysctl(KERN_PROC, KERN_PROC_PID)` → `kp_proc.p_starttime` under `#[cfg(target_os = "macos")]`, and correct the doc comment. | Nothing is stolen; an abandoned session is unrecoverable on macOS for as long as an unrelated process holds the recycled PID — an operator-visible refusal that the doc comment says cannot happen. |
