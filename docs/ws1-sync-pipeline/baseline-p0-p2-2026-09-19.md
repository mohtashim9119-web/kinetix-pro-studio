The CC task cites two historical reports: one machine "3891 passed + 33 failed"
(= 3924 total, non-skip), another "3925/0". `3891+33=3924`, not `3925` — a
1-test discrepancy the task asked to be named.

Findings from this pass, run fresh on the merged tree:

- This run's non-skip total is **3890+34=3924** — matching the *first*
  historical report's total (3924) almost exactly, with the pass/fail split
  shifted by one in each direction (3891→3890, 33→34). A single flaky/
  environment-sensitive test flipping outcome between runs is consistent with
  this and does not itself change the total.
- The `.work-phase4/replay/` fixture-presence mechanism explains **why** one
  machine had 0 failures where another had ~33 (fixtures present vs. absent —
  confirmed above), but a pure presence/absence flip moves failures into
  passes without changing the total (still 3924), so it does **not** by
  itself explain a 3924-vs-3925 total mismatch.
- One concrete state-dependent mechanism was found that *can* change which
  tests exist to be counted at all: `scripts/ws1-session-an-step5-173.test.ts:90`
  uses `it.skipIf(!existsSync(...))` — vitest still counts a skipped test in
  its total, so this alone doesn't add/remove from the grand total either, but
  it demonstrates the suite already has fixture-presence-conditional test
  registration, the same class of mechanism that could produce a total-count
  drift of exactly one test between two machines/checkouts (e.g., a test file
  present in one checkout's `scripts/` tree but not another's, or a test that
  only registers when a companion fixture file exists via a top-level
  `if (existsSync(...)) it(...)` rather than `it.skipIf`).
- **Not resolved to a single named test.** The two historical reports were
  paraphrased summary lines only (no full `--reporter=json` output was
  available to this pass to diff test-by-test). **OPEN**: to close this,
  re-run both machines with `vitest run --reporter=json` and diff the test-ID
