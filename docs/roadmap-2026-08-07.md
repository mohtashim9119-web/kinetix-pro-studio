## D4. The 50/50 question

**Verdict: CLEANLY DECOUPLABLE. [MEASURED]**

**What it is** (`git show 210855d -- src/services/snapBoundaries.ts`, quoted in full during
investigation): a rewrite of `snapCoveredBoundaries` in `src/services/snapBoundaries.ts`
(319 changed lines: 183 added / 138 removed) plus ~25-30 lines of plumbing in `src/App.tsx`,
confined to the Apply-Sync code path. It **replaces** the existing contention-aware
silence-claiming system (the 3-pass window/assign/resolve machinery CLAUDE.md documents for
`snapBoundaries.ts`, shipped 2026-07-30) as the boundary-*placement* mechanism: the boundary
between two covered segments is set unconditionally to
`(lastSpokenEnd + nextSpokenStart) / 2` — the silence between two speech events, split
exactly in half. The old candidacy predicates (`fillsTokenGapWithinSpan`, `isBreathSilence`,
`isBoundarySilenceCandidate`) are **kept, not deleted**, but repurposed: they no longer
choose where the boundary goes, only whether the committed 50/50 boundary happens to land
inside something they'd classify as a breath — reported via a new `BreathClip`
audit/logging mechanism (`onBreathClip` callback, wired in `App.tsx` to a sync-log entry),
never acted on. The commit's own comment is explicit about the trade: *"Do not change the
rule — I ruled 50/50."*

**Dependency map** (`git show 210855d`, confirmed by import-graph inspection, not inferred):

| Touch point | Classification |
|---|---|
| `src/services/snapBoundaries.ts` — the entire implementation, `BreathClip` interface, rewritten `snapCoveredBoundaries` | **SYNC-SIDE.** Imports only `types.ts`, `silenceDetector.ts`, `whisperService.ts` — confirmed via direct import-line inspection of the park commit's version. Zero imports from `dragCascade.ts`, `timelinePartition.ts`, or any editor/UI file. |
| `src/App.tsx` — `breathClips` collection, the `onBreathClip` callback wire-up, the resulting `SyncLogEntry` | **SYNC-SIDE.** Confined entirely to the Apply-Sync handler — the same function block that already calls `applyAnchorBasedTiming` and `alignFromCache`. Not the drag/lock/editor code paths. |
| `syncLog.ts` (`makeSyncLogEntry`) | **SHARED**, but pre-existing, unmodified infra already used by a dozen other sync-run log types — not a new coupling. |
| `dragCascade.ts`, `timelinePartition.ts`, lock-toggle UI | **NONE.** Confirmed by import inspection in both directions: neither file imports the other's module, and `timelinePartition.ts` references "50/50" only in a header comment describing it as a conceptual peer producer, never calling into `snapBoundaries.ts`. |

Zero required EDITOR-SIDE dependencies — the clean-decouple bar this investigation was
asked to check against.

**Is 50/50 a consequence of Model P, or an independent preference? [ASSERTED, cited]**

**Independent preference — not a consequence.** Model P's gapless requirement (ruling
point 1) only demands that *some* deterministic, non-negative split of the ambiguous
silence between two segments exists and sums to the whole — it is agnostic to *how* that
silence is divided. The codebase's own prior precedent for "how" is **not** 50/50:
`headExtendFirstSegment` gives segment 1 the *entire* lead-in silence (100/0), and Option A
(owner decision 8) gives the preceding segment the *entire* unscripted-heading gap (100/0).
50/50 is a distinct, separately-numbered ruling point (`timelinePartition.ts`'s own header:
"ruling point 2," separate from "ruling point 1" the gapless invariant) — a specific
timing/aesthetic choice that happens to also make gaplessness trivial to guarantee (a fixed
formula can never leave a gap, unlike a silence-search-and-assign system, which needed the
appended contiguity-fix safety net CLAUDE.md documents for the pre-50/50 code). It is not
*derived from* gaplessness; it is a choice that *coexists conveniently* with it.

**Does it duplicate, extend, or conflict with `snapBoundaries.ts`'s existing contention-aware
claiming? [MEASURED]**

**Neither extend nor duplicate — it supersedes.** The existing 3-pass contention-aware
assignment (Pass 2 in the pre-50/50 code: compute windows, assign contested silences by
closest spoken-midpoint, resolve left-to-right) is **deleted outright** in the park commit's
diff, not built alongside it. The predicates that used to feed that assignment are retained
only for the new breath-audit side-channel. This is a full replacement of the placement
algorithm within the same function, which is *why* it decouples cleanly: it's an in-place
rewrite of an already sync-side file, not new logic bridging sync and editor concerns.

**What this changes about the split:** nothing needs to move — **it is already on the WS1
side of the line** in the park commit. There is no WS2 code to extract it from. The
"decoupling" question dissolves into "does WS2 have any dependency that would break if this
lands" — and per the import-graph evidence above, it does not.

**What breaks in WS2 if it moves out (i.e., lands as pure WS1 work):** nothing. WS2's own
files (`dragCascade.ts`, `timelinePartition.ts`, lock UI) never call `snapCoveredBoundaries`
and never import `BreathClip`. The only WS2-adjacent consideration is that `timelinePartition.ts`'s
positioner is the *downstream consumer* of the durations 50/50 produces (same as it consumes
`applyAnchorBasedTiming`'s and `computeDragCascade`'s durations) — a data dependency, not a
code dependency, and not evidence against decoupling: any duration-producing function can be
this positioner's input.

**What would falsify this verdict:** if a future WS2 feature needed to *display* or
*recompute* a 50/50-style split live during a drag (e.g., a "preview where sync would place
this boundary" affordance) — none exists today, and the park commit builds none. If that were
built, it would create a genuine new WS2→WS1 dependency this analysis doesn't currently see.

## D9 — the follow-up pass, and what a stale brief cost (2026-08-08, later the same day)

The re-scoped follow-up to D8's triage. Three things worth carrying forward.

**1. The baseline gate earned its place.** The brief for this pass was written against
pre-`f2b4c6c` state and assigned three failures that had substantially already been fixed by
D8's own commits. Nothing in the prose gave that away — the failures were described
accurately, the file paths were right, the symptoms matched. **The only signal was a test
count**: expected 1470, measured 1493. A "confirm the baseline before touching anything" step
that looks like ceremony is what stopped a day of re-fixing fixed bugs and possibly reverting
good work.

Keep the gate. Keep it *first*, before the tag, before any reading. And keep stating expected
counts in briefs — a number is falsifiable in a way a description is not.

**2. Three numbering schemes for the same defects.** The repo called the pointercancel bug F4;
the brief called it F10; the checklist calls it step 10. The repo's F2 was the brief's F4. So
"F4" identified two different defects depending on which document you had open. **Ruled:
checklist step numbers are the only identifier** (`docs/wkwebview-drag-checklist.md`'s
"Failure numbering" section carries the cross-reference table). Per-run labels are not
identifiers, and should not have been used as them in commit messages.

**3. A test suite can be clean on behaviour and blind on teardown.** D8's step-10 failure was
a leaked listener and a stale ref — and the harness's own pointercancel test passed throughout,
because it asserted on the resulting segment array and never on what the session left behind.
That is not a missing test; it is a missing *category* of test.

The fix was structural on both sides: teardown became one function called from a `finally`
(so the cleanup set cannot drift from the resolution paths again), and the harness gained a
post-condition that runs after every test with no opt-in, auditing listener balance,
swallower count, auto-scroll teardown and residual state.

Two results from that are worth keeping in mind for the next audit of this kind:

- **Switching it on failed exactly one test** — the one deliberately pinning a known bug. The
  suite really was clean. Good news, but it means the audit proved nothing by passing.
- **So it was validated by breaking something on purpose**: reverting the step-10 fix made the
  pointercancel test fail, naming the surplus armed swallower. *An audit that has never failed
  is indistinguishable from an audit that checks nothing.* Budget for the mutation step — it
  is the part that produces the evidence.

The same discipline applied to the step-4 guards, and there it changed a claim: the
render-level two-lane test was found by mutation to catch a formula divergence but **not** a
`pixelsPerSecond`-source divergence, because `renderToStaticMarkup` collapses every derivation
to one number on a first render. That limit is now written into the test file. Without the
mutation step it would have shipped reading like full coverage.

**Still open, deliberately.** The early-bail stuck-`resizingId` bug: fixing it contradicts a
*passing* test that pins the current behaviour, so it needs a ruling rather than a drive-by
edit. And checklist step 12's video-path symptoms, now properly separated in
`docs/video-segment-investigation.md` — one of which (drag-couples-playback-speed) is very
likely working as designed and needs a product decision, not a fix.

## D10 — last-segment lock, step 10 closed by decision, undo/redo designed (2026-08-08, later still)

D9's own "still open, deliberately" list named the stuck-`resizingId` bug as needing a ruling
rather than a fix. This pass ran into the *other* half of that same principle from the other
direction: two items that had already run out the automated-fix budget got resolved not by
more engineering but by an explicit owner decision, and the decision itself is now the
artifact worth reading, not a diff.

**Step 4 stopped being a bug to fix and became an operation to remove.** D9's zoom-basis
freeze (`Timeline.tsx`) was a real, reasoned fix for the observed rescale — and it failed
manual retest twice anyway. At that point the more engineering was the wrong lever: the
freeze was fighting a symptom of an operation (drag the last edge, change total duration) that
had never been given a semantic ruling in the first place. `docs/decisions/2026-08-08-last-
segment-edge.md` names the three candidate semantics and rules option (i) — the operation is
gone, not re-fixed. The generalised form of that ruling ("no drag may change total duration")
turned out to have two MORE reachable entry points beyond the one edge anyone had tested,
found by reading the cascade code rather than by another manual pass — which is the argument
for the property test (`dragDurationInvariant.test.ts`) added alongside it: a rule stated as
an exhaustive sweep closes a bug *class*, where a rule stated as a single scenario closes one
instance and leaves siblings for the next manual run to find.

**Step 10 is the second instance of the same shape, called out explicitly this time.** Not
fixable at acceptable cost — a real OS gesture takeover in WKWebView, unreachable by any
`jsdom`-based test by construction, no matter how much more teardown-audit machinery gets
built on top of what D9 already shipped. Closed by owner decision rather than left to rot as
an unresolved manual-only row. The interesting part is the mitigation it was traded for:
**undo/redo doesn't fix the platform gap — it changes what the gap costs.** An interrupted
drag that dirties state stops being a data-loss risk and becomes a one-keystroke annoyance.
That reframing is why undo/redo was designed in the same pass rather than filed as unrelated
future work: it is the direct, stated consequence of closing step 10, not a separately

## WS2, fourth pass (2026-08-08) — step 10 REOPENED AND FIXED; undo/redo BUILT

acceptable cost" — was wrong, and the reason it was wrong is the transferable part: three

coverage is green, measure what the platform delivers before editing the handler again. Both

## D12. Video-segment drag decouples `duration` from `playbackSpeed` — RULED A BUG, QUEUED (2026-08-08)

**Ruling: it is a bug** (owner, 2026-08-08). Option 3 of the three put forward —
decouple, and require playback speed to be set explicitly. **Deliberately not fixed in
the run that received the ruling**, by instruction: scope and queue it.

Full scope, mechanism, and hazards: `docs/video-segment-investigation.md` § "Symptom 2".
Summary of what makes it non-trivial, so it is not picked up as a one-liner:

- **Two coupled behaviours, not one.** `resolveDragEdge` (`src/services/dragGeometry.ts`)
  both (a) clamps a video segment's duration into the speed-reachable window
  `[clipLen/2.0, clipLen/0.5]` and (b) derives `playbackSpeed = clipLen / duration`.
  (b) is the reported symptom; (a) is the one that surprises people. Remove (b) alone
  and the speed stops moving while the drag inexplicably refuses to pass 2× clip length.
- **It inherits an unanswered product question.** With speed pinned at 1×, a video
  segment can be dragged *longer than its own clip*. What plays in the tail — freeze,
  loop, or black? **No defined behaviour exists today** in preview or either export
  path, because (a) has always made that state unreachable. Answer this before writing
  code, not after.
- **It will fail `dragGeometry.test.ts` PART 1, and should.** That block pins
  `resolveDragEdge` byte-identical to the pre-K16 expression across a 30-case sweep
  including video fixtures — its whole purpose is to stop a change in what an
  `edgeContentX` *means* from landing silently. Update it deliberately, retain the old
  values in comments, **do not weaken or delete it.**
- **No automated backstop.** The golden replay stays 3/3 byte-identical through this
  change, because no corpus project exercises an interactive drag. This is the one drag
  change with nothing catching a regression except the manual checklist.
- **Sequence with symptom 3.** The drawer slip-bar overflow is currently contained for
  video segments *by* this coupling (`duration × playbackSpeed === clipLen` forces
  `widthPct ≤ 100`). Decoupling makes that overflow reachable for video too. Land §3's
  clamp **with or before** this.

**Suggested sequencing:** symptom 3's clamp first (local to `BottomDrawer.tsx`, no
ruling needed, no timing code touched), then the product answer on tail behaviour, then
the decoupling. **Gate:** manual checklist steps 1–4, 12, 13.

**Not scheduled against WS1.** This is editor-path work and does not block sync.
